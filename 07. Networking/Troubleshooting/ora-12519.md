# ORA-12519: TNS: no appropriate service handler found

## Overview

Very similar to `ORA-12516`. The listener knows the service but cannot find a handler willing to accept the connection right now. Almost always means:

- Instance at `PROCESSES` cap.
- Shared server pool exhausted.
- Instance is starting up or shutting down — registered but not accepting.

## Diagnostic Steps

### 1. Resource limits

```sql
SELECT resource_name, current_utilization, max_utilization, limit_value
FROM   v$resource_limit
WHERE  resource_name IN ('processes','sessions','shared_servers');
```

### 2. Instance state

```sql
SELECT status, database_status FROM v$instance;
-- Expect status = OPEN, database_status = ACTIVE
```

If `STARTED`, `MOUNTED`, or `SHUTDOWN PENDING`, the instance is transitioning.

### 3. Alert log

Startup or shutdown messages in progress?

## Common Fixes

Same as `ORA-12516`:

- Kill idle sessions.
- Increase `processes`.
- Wait for startup/shutdown to complete.
- Fix application connection leak.

Force dedicated in client TNS:

```
SERVER=DEDICATED
```

## Best Practices

Same as `ORA-12516`:

1. Size `processes` with headroom.
2. App-tier connection pooling.
3. `SQLNET.EXPIRE_TIME` for dead session cleanup.
4. Alert on `V$RESOURCE_LIMIT`.
5. Retry connect in client with backoff.

## Interview Questions

1. **Q:** `ORA-12519` cause?
   **A:** Handler exhaustion — usually `PROCESSES` cap or instance transitioning.

2. **Q:** Difference from `ORA-12516`?
   **A:** Very similar. `12519` is more specifically about no available handler; `12516` about no matching protocol/handler. Fixes overlap.

3. **Q:** Retry from client?
   **A:** Yes — often transient. Set `RETRY_COUNT` in TNS description.
