# ORA-00054: resource busy and acquire with NOWAIT specified or timeout expired

## Meaning

A DDL or `LOCK TABLE ... NOWAIT` couldn't get the lock immediately.

```
ORA-00054: resource busy and acquire with NOWAIT specified or timeout expired
```

## Common Causes

- Active DML on the target table.
- Long-running query holding a query lock.
- Long-running index build.
- Missing FK index causing TM lock cascade.

## Diagnostic Queries

```sql
-- Who has the lock?
SELECT   s.sid, s.serial#, s.username, s.status, s.event,
         o.object_name, lo.locked_mode
FROM     v$locked_object lo
JOIN     dba_objects   o ON o.object_id = lo.object_id
JOIN     v$session     s ON s.sid       = lo.session_id
WHERE    o.object_name = '&table_name'
ORDER BY s.sid;

-- Session waiting to acquire
SELECT sid, username, event, seconds_in_wait
FROM   v$session
WHERE  event LIKE 'enq: TM%' OR event LIKE 'enq: TX%';
```

## Fix

**Wait it out** (usually best):

```sql
LOCK TABLE T IN EXCLUSIVE MODE;   -- blocks until free
```

**Kill the blocker** (if safe):

```sql
ALTER SYSTEM KILL SESSION '150,32458' IMMEDIATE;
```

**Retry with NOWAIT** (during retry loop):

```sql
-- App-level pattern
BEGIN
  FOR i IN 1..10 LOOP
    BEGIN
      LOCK TABLE T IN EXCLUSIVE MODE NOWAIT;
      -- do DDL
      EXIT;
    EXCEPTION
      WHEN OTHERS THEN
        IF SQLCODE = -54 THEN
          DBMS_SESSION.SLEEP(30);
        ELSE
          RAISE;
        END IF;
    END;
  END LOOP;
END;
/
```

**DDL_LOCK_TIMEOUT** (12c+):

```sql
ALTER SESSION SET ddl_lock_timeout = 300;   -- wait up to 5 min for DDL
ALTER TABLE T ADD COLUMN c NUMBER;
```

## Prevention

- Schedule DDL in maintenance windows.
- Add FK indexes.
- Kill runaway sessions ahead of maintenance.
- Use `DDL_LOCK_TIMEOUT` on scripted deployments.
