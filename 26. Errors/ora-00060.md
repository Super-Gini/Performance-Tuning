# ORA-00060: deadlock detected while waiting for resource

## Meaning

Oracle detected a cycle in session-wait graph and rolled back the current statement of one victim session.

```
ORA-00060: deadlock detected while waiting for resource
```

The victim's **transaction is preserved** — only the current statement is rolled back. The application must handle by rerunning or aborting the whole transaction.

## Common Causes

- Two sessions updating same rows in opposite order.
- FK deletions without FK indexes → TM lock cascades.
- Bitmap indexes on OLTP tables.
- Batch UPDATE + single-row UPDATE hitting same rows out of order.

## Diagnostic Queries

```sql
-- Recent deadlocks (from alert log)
SELECT originating_timestamp, message_text
FROM   v$diag_alert_ext
WHERE  message_text LIKE '%ORA-00060%'
  AND  originating_timestamp > SYSDATE - 7
ORDER  BY originating_timestamp DESC;

-- Deadlock trace files
SELECT trace_filename, modify_time
FROM   v$diag_trace_file
WHERE  trace_filename LIKE '%deadlock%'
  AND  modify_time > SYSDATE - 7
ORDER  BY modify_time DESC;
```

Open the trace file to see the deadlock graph and SQL text.

## Fix

**Immediate**: Rerun the transaction (from the victim's side).

**Root cause**: See [Deadlocks](../13-locking/deadlocks.md).

Typical patterns:

- Fix update order — always sort by PK: `UPDATE ... WHERE id IN (...) ORDER BY id`.
- Add missing FK index.
- Replace bitmap indexes with B-tree on high-DML tables.
- Reduce batch size.

## Prevention

- Consistent access order across the application.
- Application-level retry with backoff.
- Missing FK index audit (see [Deadlocks](../13-locking/deadlocks.md)).
